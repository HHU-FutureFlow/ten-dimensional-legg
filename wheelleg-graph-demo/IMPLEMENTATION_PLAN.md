## 2. 便携、共享与开源准备

### 2.1 支持的使用方式

| 使用方式 | 预期行为 | 数据归属 |
| --- | --- | --- |
| 单人本机运行 | 在自己的电脑启动服务，用浏览器编辑，agent 连接该服务 | 该实例的数据目录 |
| 分享项目文件 | 导出 JSON，队友在自己的实例导入；源码可以暂时不可用 | 导入后是独立副本，不声称实时同步 |
| 团队共同编辑 | 团队主机/服务器启动一个服务，人和 agent 连接同一地址 | 同一个权威服务，所有人共享 revision |
| 将来开源 | 工具代码可作为独立仓库分发，使用通用示例和公开说明 | 代码许可、公开示例和发布范围由用户后续决定 |

“本地应用”仅代表一种运行方式。前端不能将 `localhost`、当前用户名或当前工作区位置写成固定的业务依赖。

### 2.2 首版必须做到的可迁移性

- 工具代码、文档、示例和启动流程可从独立目录使用；不依赖 Wheelleg 父目录的私有脚本、全局 skill 或某个 agent 的缓存。
- 使用标准 Node.js/npm 运行和构建；实施时确认并声明测试过的 Node 版本、`engines` 约束及依赖锁文件。不要凭当前机器的 PATH 推导队友也能直接运行。
- 提供通用 npm 命令；Windows 启动脚本只是便利入口，macOS/Linux 可以按 README 使用相同服务。
- 提供容器构建和数据卷配置，作为队友和团队服务器的复现入口；容器未实际验证时明确记录限制。
- 服务地址、监听端口、数据目录和访问凭据可配置；提供无秘密信息的配置示例。
- 前端通过可配置的同源 API 地址访问服务，不把构建机磁盘路径或服务地址烘焙进业务数据。
- 项目文件只保存可分享的逻辑信息；用户机器上的源码目录绑定、访问令牌和本地偏好放在忽略的本地配置中。
- 样例能在没有机器人源码的机器上打开和编辑；源码位置显示为可选关联信息。
- 新电脑不必先拥有 Codex、EmberProbe、Python、MATLAB、STM32 工具链或当前固件仓库，才能运行工程地图。

### 2.3 源码位置的逻辑映射

图中记录 `rootId + 相对路径 + 符号 + 可选行号/版本`，不记录开发者绝对路径。例如：

```json
{
  "rootId": "firmware",
  "path": "application/chassis/LQR.c",
  "symbol": "LQR_calc",
  "line": 71,
  "revision": "a7d8f90"
}
```

`firmware` 在每台机器上可以绑定不同目录，也可以暂不绑定。未绑定时仍可查看和编辑图。首版提供源码定位信息的显示与复制；不承诺任意浏览器直接打开本地编辑器，也不扫描源码或自动修正行号。

### 2.4 开源前的工程组织

- 运行时配置、用户数据、凭据、构建缓存和依赖目录与可分发源码分离。
- README 使用通用命令和相对路径，不能只有当前开发者电脑上的绝对地址。
- 本方案中的 Wheelleg 绝对路径仅用于本次实施定位，不能复制成工具运行常量。
- 记录直接依赖及许可证来源；正式 `LICENSE` 类型和仓库公开发布由用户决定。本次不替用户选择代码许可或对外发布。
- 不把完整固件、内部记忆、个人目录配置或生成图片缓存作为工具的必需分发文件。
- LQR 示例是独立数据资产，应注明来源、梳理版本和验证范围；实际公开前由用户确定是否随工具发布。

## 3. 技术架构

建议：React + TypeScript + React Flow 前端，Node.js 本地/自托管服务，项目 JSON 持久化，CLI 调用同一服务。

```text
人：浏览器画布 ─────┐
                  ├─ HTTP 命令 / 查询 ─ 权威服务 ─ 校验与事务 ─ 项目 JSON
agent：CLI ────────┘                       │                └─ 恢复备份
                                          └─ 事件通知 ─ 浏览器更新

README / AGENT_GUIDE / SKILL → 指导维护者使用上述接口，不参与自动理解工程
```

- 服务持有项目当前 revision；界面和 CLI 都不绕过服务直接覆盖活动项目文件。
- 使用 HTTP 查询和事务提交；前端用 SSE 或等价方式接收 revision 更新。事件流的鉴权方式与团队模式一起落实，不把访问令牌放进可分享 URL。
- 所有编辑走共用的领域操作与校验，不能分别在前端和 CLI 实现不一致的修改规则。
- 服务端文件持久化是权威数据；浏览器缓存仅用于偏好或暂存，不能成为唯一保存位置。
- 同一数据目录由一个服务实例写入；多个浏览器和 agent 可以连接它。检测并拒绝第二写入实例，避免误认为不同端口即实现安全共享。
- 节点 ID、端口 ID 等来自稳定生成器，不能用显示名称或数组下标替代。

当前技术参考：

- [React Flow 端口](https://reactflow.dev/learn/customization/handles)
- [React Flow 保存与恢复](https://reactflow.dev/examples/interaction/save-and-restore)
- [Rete.js](https://retejs.org/docs/) 仅作为曾比较的路线，不同时引入第二套图引擎。

已实施：Node >=24（实测 24.14.0）、React 19.3.1、React Flow 12.12.1、Vite 7.3.8、TypeScript 5.9.3，完整版本由 package-lock.json 固定。本目录和独立目录均已安装、构建及运行；见验证记录。

## 5. 数据模型建议契约

### 5.1 单项目文档

采用一个项目 JSON 封装工程模型与视图布局，逻辑上分开，保存时可作为一个事务落盘，避免两个权威文件更新一半。

```json
{
  "schemaVersion": 2,
  "projectId": "example-project",
  "title": "空白工程",
  "revision": 0,
  "rootSceneId": "root",
  "sourceRoots": { "firmware": { "label": "固件工程" } },
  "model": {
    "nodes": {},
    "ports": {},
    "edges": {},
    "groups": {},
    "scenes": { "root": { "id": "root", "label": "工程总览", "description": "" } }
  },
  "view": {
    "nodes": {},
    "edges": {},
    "groups": {},
    "scenes": { "root": { "viewport": { "x": 0, "y": 0, "zoom": 1 } } }
  }
}
```

此例与已实现的 v2 项目封装一致，Schema 已写入 schema/。机器上的源码根目录绑定不写入 `sourceRoots` 的可分享部分；当前仅显示/复制源码引用，不读取源码。

### 5.2 对象和职责

| 对象 | 必要/主要字段 | 说明 |
| --- | --- | --- |
| 节点 Node | id、sceneId、label、description、kind、status、sourceRefs、metadata、可选 groupId/detailSceneId | 功能抽象不必一一对应文件或函数 |
| 端口 Port | id、nodeId、direction、label、dataType、shape、unit、coordinateFrame、order、description | 支持标量/向量/矩阵等描述，未知信息允许空缺 |
| 连线 Edge | id、sourcePortId、targetPortId、label、kind、condition、description | 保留数据/控制等语义，条件是说明而非可执行代码 |
| 分组 Group | id、sceneId、label、description、可选 parentGroupId | 同层分组；分组关系禁止循环 |
| 独立视图 Scene | id、label、description、可选 ownerNodeId | root 无 owner；子视图与父节点 detailSceneId 互相对应 |
| 节点视图 | position、size、折叠及显示偏好 | 更新语义不应重排用户布局 |
| 连线视图 | style、waypoints、标签位置 | 默认贝塞尔；中间走线点与端口端点分开 |
| 分组视图 | position、size、collapsed | 收起时映射边界显示，底层真实端口连接保持不变 |
| 各层视角 | view.scenes[sceneId].viewport | 每层独立保存位置和缩放 |

状态至少区分“源码已实现”“设计中”“待核实”，验证证据另外记录，不能把“已实现”直接等同于“本轮已实测”。

模型支持控制系统常见的反馈环；不要套用工作流 DAG 假设禁止所有环。禁止的是非法对象引用和分组层级循环。

### 5.3 校验策略

- 拒绝重复 ID、悬空引用、错误的端口所属关系和输入输出方向错误。
- 默认输出端口允许扇出；输入多连接策略要明确配置，不能默默覆盖旧连接。
- 已知且明确冲突的数据类型/维度提示具体位置；未知类型、可疑单位或坐标系采用提示，不能声称完成物理正确性验证。
- 删除有关联连线的节点/端口时，默认提示影响；只有显式级联操作才一并删除相关连线和视图记录。
- 不因重命名节点而改变 ID；不因参数或说明变更而自动删除位置和连线。
- 新版 Schema 不可被旧版工具静默覆盖；不支持的版本应拒绝并说明。
- 本版按用户更正仅接受 v2；不迁移 v1，默认 data/v2 与旧文件隔离。端口 parentPortId 表达父子接口，普通连线及分组禁止跨视图。
- 文档、公式、条件和 metadata 都作为数据处理，不作为脚本执行。

## 6. 事务、共同编辑与落盘

### 6.1 提交协议

建议事务结构：

```json
{
  "requestId": "unique-request-id",
  "baseRevision": 12,
  "actor": "codex",
  "summary": "补充 LQR 悬空控制输入",
  "operations": [
    {
      "op": "port.add",
      "value": {
        "id": "lqr-air",
        "nodeId": "lqr",
        "direction": "input",
        "label": "air",
        "dataType": "bool",
        "unit": "",
        "shape": "",
        "coordinateFrame": "",
        "order": 0,
        "description": "悬空门控输入",
        "multiplicity": "one"
      }
    }
  ]
}
```

建议操作覆盖 node、port、edge、group 的 add/update/remove，以及独立的 view 更新。更新使用字段补丁，避免要求 agent 发送整个项目文档。禁止把 `view` 重置为默认值作为普通语义更新的副作用。

### 6.2 必须保持的行为

1. 校验 `baseRevision` 与服务当前版本；过期提交返回明确的冲突信息，不强行覆盖。
2. 在临时副本上完整应用和校验一组操作；全部成功才作为一个新 revision 提交。
3. 在项目级队列内串行处理写入，保持内存与磁盘版本一致。
4. 正常文件写入采用临时文件、校验、替换及上一版本恢复备份；写入失败时不广播成功或晋升内存版本。
5. 对文件系统失败和 Windows 路径空格进行实测；不要把“使用 rename”写成已经验证断电不丢数据。
6. `requestId` 用于识别短期重试，避免网络重试重复添加节点；说明跨重启的保障范围。
7. 事务成功后通知其他客户端；客户端断线重连时查询最新完整状态，不假定收到全部事件。
8. 若检测到运行期间活动项目文件被外部改写，拒绝盲目覆盖并提示重新加载/导入。正常 agent 编辑使用 CLI。
9. 导入默认创建独立项目身份；替换已有项目必须显式选择并带版本检查。

首版使用乐观并发控制，不承诺把所有并行编辑自动合并。发生冲突后，重新读取当前图，保留本次编辑意图，再生成只涉及所需字段的新补丁；禁止用旧整图重放覆盖。

### 6.3 撤销与重做的边界

- 拖动结束作为一次布局事务，避免每帧形成一个可撤销版本。
- 记录事务涉及的对象和逆操作；不通过整份旧项目覆盖后来他人的内容。
- Demo 可以采用保守策略：仅允许撤销本 actor 位于全局最新位置的操作；若其后存在别人的操作，拒绝直接撤销并说明。
- 重做同样检查版本和对象状态，不盲目执行过期逆操作。
- 首版可以只保存会话内撤销栈；关闭服务后图的数据必须保留。撤销栈的持久化范围写进 README。

### 6.4 团队运行配置

- 默认监听回环地址；团队部署通过显式配置启用。
- 团队模式需要访问凭据，查询、写入及事件通知使用一致的访问控制；不能仅把监听地址改成所有网卡便宣称完成团队部署。
- API 的项目参数不能成为任意磁盘路径写入接口；活动数据限制在配置的数据目录内。
- 用户数据挂载在独立卷/目录，重建服务镜像不应删除项目数据。
- 首版团队模式可共享一组访问凭据，actor 用于区分修改来源；不承诺角色权限或身份审计系统。

## 8. CLI、API 与 agent skill

### 8.1 CLI 是实际操作入口

已实现的命令形式（更多操作见 docs/API.md）：

```text
npm run graph -- list
npm run graph -- inspect --project <id>
npm run graph -- validate --file ./examples/lqr.graph.json
npm run graph -- apply --project <id> --file ./examples/patches/add-air.json
npm run graph -- export --project <id> --out ./export.graph.json
npm run graph -- import --file ./export.graph.json
```

- 服务地址和凭据通过通用配置或命令参数提供，不能默认只有当前机器上的固定端口可用。
- `inspect` 返回稳定、可机器读取的 JSON，包括 revision、ID 和必要布局信息；大图支持按对象查询。
- `apply` 使用补丁内的 `baseRevision`，支持仅校验而不提交的 dry-run。
- `validate --file` 可离线检查结构，不能修改活动项目；在线修改统一走服务。
- 正常输出 JSON；错误提供非零退出码、稳定错误码和可读说明；不把凭据打印进输出。
- 不强制 agent 通过浏览器点击，不要求截图识别节点，也不要求修改压缩后的界面内部数据。

API 文档至少覆盖项目列举/新建/读取、事务提交、结构校验、导入导出、事件通知、团队鉴权及错误示例。具体路由与 CLI 使用同一领域层。

### 8.2 通用 agent 操作流程

1. 读取工具指南和当前任务授权；需要理解工程时由 agent 自行阅读源码。
2. 查询目标项目及最新 revision，获取相关节点/端口的稳定 ID。
3. 整理证据、待确认项和修改意图，不把推测标成已实现事实。
4. 创建最小补丁，保留未涉及的语义和用户布局。
5. dry-run 校验；提交；冲突时重新读取并重新生成补丁。
6. 检查提交结果及 revision，报告具体改动和仍待核实的关系。

### 8.3 skill 与文档的职责

- `docs/AGENT_GUIDE.md` 是跨 agent 的完整说明，不依赖某个厂商的 skill 自动发现机制。
- `skills/project-graph/SKILL.md` 是轻量入口，包含适用条件、标准流程、CLI 入口和文档引用。
- skill 随工具交付，不自动写入 Codex/WorkBuddy/Trae 的全局配置；具体安装方式留在说明中。
- 编写 skill 时读取当前可用的 skill-creator 指南；本轮只规划，没有创建 skill。
- 使用 agent 自身能力阅读源码和操作 CLI；不要求工具接入某个模型 API 或额外持有模型密钥。

示例由维护者阅读源码后人工/agent 建立。数据格式必须通用，不能把 LQR 专用字段写死到编辑器组件里。

| 功能抽象 | 参考实现 | 示例应表达的内容 |
| --- | --- | --- |

## 14. 必须防止的范围误读

1. “长期根据工程状态更新”指维护者能够更新；首版不要求工具自动发现工程变化。
2. “实时共同编辑”指同一服务下的图数据更新；不代表机器人实时遥测。
3. “分享 JSON”产生独立副本；两个人各自打开副本不等于共同编辑同一项目。
4. “可开源”要求架构和分发可独立；不代表本轮已授权选许可证、创建公开仓库或上传资料。
5. “可记录源码位置”不代表任何浏览器都能打开服务器/客户端的任意本地文件。
6. “有 skill”不代表其他 agent 自动读过它；交接必须明确给出通用指南/skill 入口。
7. “有 JSON 文件”不代表同时覆盖写就安全；活动项目的共同编辑必须遵守事务入口。
8. “效果图好看”不代表所有控件都已实现；交付截图和验收记录来自实际工具。
9. 不要把自动排布节点与自动理解源码混为一谈；复杂自动布局也不是首版验收条件。
10. 文档任务曾仅授权文档；用户已在随后明确授权实施，以 §0 当前授权和本节最新记录为准。
