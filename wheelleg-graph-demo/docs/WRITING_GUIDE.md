# 让节点能够独立解释自己的功能

读者应能从图中知道“接收什么、怎么处理、输出什么、在什么条件下得到什么结果”，无需先记住变量名或状态编号。源码符号用于对照位置，中文说明负责解释含义。

## 分配内容

- **功能块**：说明这一块接收、处理和输出的具体内容，以及分支规则。
- **判定块**：列出输入、比较方式、各条件和结果；说明是否互斥、先后覆盖或优先级。
- **说明板**：解释全图目的、名词、编号、符号、单位、坐标系、参数表和阅读顺序；不接线。
- **子视图**：展示父功能块的内部结构，边界和上层接口保持对应。

核心工具适用于软件、硬件与其他流程，不把 LQR/机器人状态写死到通用模型。电气接线与软件数据流分别定义端口和关系；当前连接方向为输出到输入。

## 功能说明四字段

`metadata.explanation` 包含：

```json
{
  "receives": "左右腿目标摆角、实际摆角、连续达标时间和阶段用时。",
  "process": "每拍比较两条腿的角误差，一条腿不达标就把连续计时清零。",
  "produces": "下一阶段的选择，以及交接时要清零的斜坡状态。",
  "decisions": [
    "阶段用时超过 8 秒 → 转入翻身等待，超时结果优先。",
    "未超时，两腿误差都小于约 5.7 度并连续保持半秒 → 进入平衡接管。",
    "其余 → 继续当前蹬地阶段；不额外等待腿长到位。"
  ]
}
```

这个示例依据当前固件 S3 退出条件，不能不核对源码就挪用于其他项目。

### 接收

交代来源与含义。目标值与实际反馈分开；多个标志要说明各代表什么。图内使用“观测包”等收纳接口时，列出该块真正读取的字段，并说明它是图内别名。

### 处理

解释怎样由输入得到结果。需要公式时先用中文讲作用，再给公式/变量对照；例如“角度偏差提供纠偏力矩，角速度提供阻尼”。若只是整理连线，明确不做额外计算。

### 输出

写具体量、去向和单位；注明后续是否仍可覆盖。某条候选路径不生效时，不把它写成一直在向下游产生控制量。

### 判定

每条包含条件和结果。数值带单位，说明连续驻留而非累计时间；未满足和超时分支都要交代。源码中后续独立 if 能覆盖前面的结果时，说明该优先级。

状态先给中文名称，再把 S0 等编号放在旁边。监控有开关时写明开关与当前默认值，不能因为源码存在就暗示始终启用。

## 说明板

使用 kind=annotation，description 为 Markdown，metadata.boardTone 可选 amber/teal/slate。说明板没有端口或子视图，不显示功能块的输入输出计数及实现状态。

每层入口优先提供必要词典。例如恢复状态页先解释 S0～S7 的目的与退出依据；执行页先解释 Tw/Tp/F_leg 和单位。长表格可滚动，宽高可调整。

## 连线与真实性

- data：实际或图内明确打包的数据传递。
- control：条件判定结果。
- transition：阶段转移，虚线；使用判定/事件端口。
- force：力或力矩通道。

箭头应能由功能输入输出解释。纯恢复 PD 不读取原始 LQR 力矩，就不为了排版把 LQR 数据线接进去。直接读全局目标/观测时，尽量补出对应接口；省略部分须在说明中指出来源。

## 维护示例与检查

LQR 示例生成顺序：`create-examples.mjs` 建主链，`detail-example.mjs` 建层级，`explain-lqr.mjs` 补实际依赖并覆盖最终文案，`lqr-boards.mjs` 写展板。改文案应修改最终来源，再运行生成脚本。

审核时检查：不看源码能否说出输入输出？编号/缩写是否先解释？条件是否有结果和默认路径？候选结果会不会被误读成相加？数值是否对应当前源码？源码已实现和本轮实测是否区分？
